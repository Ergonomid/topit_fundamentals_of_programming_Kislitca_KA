## Задание 1. Условия и классификация данных

### Порядок проверки условий

В `check_ranges()` для каждого значения используется цепочка `if / elif / else`,
поэтому для одного значения срабатывает не более одной ветви:

1. `score < 0` — слишком мало;
2. `elif score > 100` — слишком много;
3. `else` — значение корректно, ошибка не добавляется.

Аналогично для `absences` (< 0, > 5, иначе корректно).

В `level_by_score()` проверки идут **от лучшего уровня к худшему**:
`score >= 90` → `>= 75` → `>= 60` → `else`. Такой порядок позволяет
не писать двойные условия вида `75 <= score <= 89`: если значение не прошло
предыдущую ветвь, верхняя граница уже гарантированно меньше.

**Какие ветви недостижимы.** При выбранном порядке:

- в `level_by_score()` недостижима «верхняя» граница каждого диапазона —
  условия `score <= 100` и т. п. писать не нужно, они выполняются по построению;
- в `check_ranges()` при корректном ходе вычислений ветви `else` внутри
  каждой цепочки — это нормальный путь для корректных данных, а не ошибка;
- недостижимо одновременное срабатывание двух ветвей одной цепочки:
  `score < 0` и `score > 100` взаимоисключающи, потому что стоят в `elif`;
- если поменять порядок на «от худшего к лучшему» (`>= 60` раньше `>= 90`),
  то ветви `>= 75` и `>= 90` стали бы **недостижимыми**: все значения 60–100
  перехватывались бы первым условием.

### Снижение уровня за пропуски

ниже «недостаточный». Ступени: недостаточный (0) → удовлетворительный (1) →

## Задание 2. Циклы и базовые алгоритмы

### Результаты по исходным измерениям

```text
[12, 15, 11, 18, 18, 9, 21, 15, 7, 18]
Сумма:           144
Минимум:         7
Максимум:        21
Чётных:          4
Среднее:         14.400
Выше среднего:   6
```

Пункты «сумма / минимум / максимум / чётные» вычисляются в одном цикле
`aggregate()`. Пункт «выше среднего» требует **второго** прохода: среднее
становится известно только после накопления суммы.

### Сложность алгоритмов

| Алгоритм | Время | Доп. память | От чего зависит |
|----------|-------|-------------|-----------------|
| `aggregate()` (сумма, min, max, чётные) | O(n) | O(1) | число элементов n |
| `mean()` / `count_above_mean()` | O(n) + O(n) = O(n) | O(1) | n |
| `linear_search()` | O(n) (худший случай) | O(1) | позиция элемента / n |
| `is_prime()` | O(√n) | O(1) | значение числа n |
| `selection_sort()` | O(n²) | O(n) на копию | n, сравнений n(n−1)/2 |
| `binary_search()` | O(log n) | O(1) | n, сравнений ≈ log₂n |

**Почему ограничение делителей квадратным корнем корректно.** Если число
составное, то n = a · b, где 1 < a ≤ b < n. Тогда a ≤ √n: меньший из двух
делителей всегда лежит в диапазоне 2…√n. Значит, достаточно проверить
делители до √n включительно — если ни один не подошёл, число простое.
Дополнительно проверяются чётность и случаи n < 2, поэтому шаг перебора
можно увеличивать на 2, проверяя только нечётные делители.

### Псевдокод: сортировка выбором

```text
алгоритм SelectionSort(A):
    для i от 0 до длина(A) − 2:
        min_index ← i
        для j от i + 1 до длина(A) − 1:
            если A[j] < A[min_index]:
                min_index ← j
        если min_index ≠ i:
            обменять A[i] и A[min_index]
    вернуть A
```

Сложность: внешний цикл (n−1) итераций, внутренний — n−i−1 сравнений,
итого n(n−1)/2 сравнений → **O(n²)**; обменов не больше n−1.

### Псевдокод: бинарный поиск

```text
алгоритм BinarySearch(A, target):   # A отсортирован
    low ← 0
    high ← длина(A) − 1
    пока low ≤ high:
        middle ← (low + high) // 2
        если A[middle] = target: вернуть middle
        иначе если A[middle] < target: low ← middle + 1
        иначе: high ← middle − 1
    вернуть −1
```

Сложность: на каждом шаге область поиска уменьшается вдвое,
итого не более ⌊log₂n⌋ + 1 итераций → **O(log n)**, память O(1).

### Сравнительная таблица числа сравнений

Искалось значение, которого в наборе нет (худший случай для линейного поиска).
Данные: `[(i * 37) % n for i in range(n)]`.

| n | линейный поиск | бинарный поиск | выигрыш |
|--:|---------------:|---------------:|--------:|
| 10 | 10 | 8 | 1.3× |
| 100 | 100 | 14 | 7× |
| 1000 | 1000 | 20 | 50× |

При росте n число сравнений линейного поиска растёт пропорционально n,
бинарного — как логарифм. Основной результат — именно число сравнений,
а не время: измерения времени зависят от машины и шума.

## Задание 3. Коллекции и выбор структуры данных

### Построенные структуры

```text
1. Множество студентов:   ['anna', 'boris', 'daria']
2. Множество работ:       ['lab_01', 'lab_02']
3. Попытки по студентам:
   anna   [('lab_01', 5), ('lab_02', 5), ('lab_01', 4)]
   boris  [('lab_01', 4), ('lab_02', 5)]
   daria  [('lab_01', 3)]
4. Лучшие результаты:     anna/lab_01 -> 5, anna/lab_02 -> 5,
                          boris/lab_01 -> 4, boris/lab_02 -> 5, daria/lab_01 -> 3
5. Количество попыток:    anna/lab_01 -> 2, anna/lab_02 -> 1,
                          boris/lab_01 -> 1, boris/lab_02 -> 1, daria/lab_01 -> 1
```

Студенты, сдававшие обе работы (пересечение множеств `lab_01 ∩ lab_02`):
**anna, boris**. Объединение множеств даёт `anna, boris, daria`.

### Инкрементальное обновление

`SubmissionIndex.add()` обновляет все пять структур за O(1) в среднем:
добавляет имя в два множества, дописывает попытку в список студента,
увеличивает счётчик и обновляет максимум по ключу. Полное перестроение
не требуется. Проверено добавлением двух записей для `daria`:

```text
До:    daria / lab_02 -> None
После: daria / lab_02 -> 4 | попыток: 2
```

### Почему выбраны такие коллекции

- **Множество** хранит только уникальные значения: добавление одного и того же
  студента дважды не создаёт дубликат. Хорошо подходит для «списка участников»
  и для операций `&`, `|`, `-`.
- **Кортеж** неизменяем, поэтому у него есть стабильный хеш — его можно
  использовать как ключ словаря: `best[(student, laboratory)]`.
- **Список** изменяем и не хешируется (`TypeError: unhashable type: 'list'`),
  поэтому ключом словаря служить не может. Кроме того, равные списки
  с разным содержимым нельзя однозначно сопоставить ключу.
- **Словарь** даёт поиск по составному ключу за O(1) в среднем вместо
  O(n) перебора списка пар. Для частых запросов «лучший результат по паре»
  это решающее преимущество.

### Оценка средней сложности

| Коллекция / операция | Добавление | Поиск | Память |
|----------------------|-----------|-------|--------|
| `set.add` / `x in set` | O(1) среднее, O(n) худшее | O(1) среднее | O(n) |
| `dict[key] = value` / `d[key]` | O(1) среднее | O(1) среднее | O(n) |
| `list.append` | O(1) амортизированное | O(n) поиск по значению | O(n) |
| `tuple` как ключ | — (неизменяем) | хеш O(len) | O(1) на кортеж |

Худшие случаи O(n) для `set`/`dict` возможны при массовых коллизиях хешей,
на практике средняя сложность близка к O(1).

### Текстовые запросы

Поддерживаются команды `student <имя>`, `best <имя> <работа>`,
`attempts <имя> <работа>`, `completed <работа>`; разбор — через `match / case`.
Неизвестная команда возвращает подсказку со списком доступных, отсутствующий
ключ — сообщение «Нет данных…», пустой запрос — предупреждение. Аварийного
завершения нет ни в одном из случаев (проверено запросами
`average anna`, `student roman`, `best daria lab_02`, пустой строкой).

### Контракты функций

|---------|------|-----------|---------------|
| `arithmetic_mean(values)` | непустой список чисел | `float`, среднее | пустой список → `nan` (ранний выход) |

### Примеры вывода

```text

Именованные: Итог: Борис — среднее 66.7, минимум 60, максимум 72, попыток 3
Распаковка списка *: Результат: Дарья — среднее 93.75, минимум 90, максимум 97, попыток 4
Распаковка словаря **: Результат: Илья — среднее 62.0, минимум 55, максимум 70, попыток 3

```

Распаковка `*values` передаёт элементы списка как позиционные аргументы,
`**{"student": ...}` — как именованные. Для `collect_tags` распаковка
позволяет собрать теги из готового списка и передать опции словарём.

### Схема областей видимости LEGB

```text
+--------------------------------------------------------------+
| B — Built-in:  print, len, ValueError, ...                   |
|   +------------------------------------------------------+   |
|   | G — Global (модуль task_4.py)                        |   |
|   |   course = "Python"      <-- НЕ изменяется           |   |
|   |   +----------------------------------------------+   |   |
|   |   | E — Enclosing (outer_scope_demo)             |   |   |
|   |   |   counter = 0    <-- изменяется через        |   |   |
|   |   |                      nonlocal в inner()      |   |   |
|   |   |   +--------------------------------------+   |   |   |
|   |   |   | L — Local (inner)                    |   |   |   |
|   |   |   |   label = "inner call #N"            |   |   |   |
|   |   |   |   counter += 1  (nonlocal — не L!)   |   |   |   |
|   |   |   +--------------------------------------+   |   |   |
|   |   +----------------------------------------------+   |   |
|   +------------------------------------------------------+   |
+--------------------------------------------------------------+
```

Порядок поиска каждого имени в `inner()`:

1. **`label`** — найдено в L (локальная область `inner`).
2. **`counter`** — в L **не** ищется: объявлено `nonlocal counter`, поэтому
   Python сразу обращается к E (`outer_scope_demo`), где `counter = 0`.
   Присваивание `counter += 1` меняет именно это имя, а не создаёт новое.
3. **`course`** — в L и E отсутствует, найдено в G (модуль). Глобальное имя
   только читается, `global` не используется, поэтому значение остаётся
   `"Python"` (проверяется через `assert`).
4. **`print`** — в L, E, G отсутствует, найдено в B (встроенные имена).

Фактический результат двух вызовов: `counter` равен `2`,
`course` равен `"Python"`.

### Ошибка изменяемого значения по умолчанию

```python
def add_result(value, results=[]):   # ошибка
    results.append(value)
    return results
```

**Жизненный цикл значения по умолчанию.** Значения по умолчанию вычисляются
**один раз** — в момент выполнения инструкции `def`, и сохраняются в атрибуте
`add_result.__defaults__`. Это тот же самый объект списка для всех вызовов,
которые не передали аргумент. Поэтому:

```text
broken(1) -> [1, 2]
broken(2) -> [1, 2]        # тот же объект! id совпадает
```

Второй вызов видит результат первого: функция накопила состояние там, где
контракт предполагал чистый вход.

**Исправление:**

```python
def add_result(value, results: list[int] | None = None):
    if results is None:
        return [value]
    return [*results, value]
```

Неизменяемый `None` безопасен как значение по умолчанию, а сам список
создаётся внутри вызова. Дополнительно возвращается **новая** коллекция,
поэтому аргумент вызывающей стороны тоже не меняется.
Проверено: `broken` возвращает один объект на два вызова,
`add_result` — разные объекты с результатами `[1]` и `[2]`,
`add_result.__defaults__ == (None,)`, переданный список `[10]` остался прежним.

### Функции высших порядков и замыкания

```text
Именованная функция is_excellent: [False, True, False, False, False]
lambda x: x >= 80:                [False, True, True, True, False]
Порог 60:                         [True, True, True, True, False]
Порог 85:                         [False, True, False, True, False]
Замыкания независимы:             [78, 84]
```

`apply_to_results(operation, values)` принимает функцию как значение
и применяет её к каждому элементу, возвращая новый список.
`make_threshold_checker(threshold)` — фабрика: в замыкании сохраняется
**параметр фабрики** `threshold` (ячейка `__closure__` с содержимым 60 или 85).
Каждый вызов фабрики создаёт независимую функцию, поэтому пороги не мешают
друг другу. Значение фиксируется в момент создания функции и не зависит
от последующих вызовов с другими аргументами.

| обычный набор данных | 4 | 13 | 79.38 | Дарья | базовый расчёт |
| один студент | 1 | 2 | 84.50 | Анна | группа из одного человека |
| несколько лидеров | 3 | 5 | 83.00 | Анна, Борис | ничья по среднему |
| пустая группа | 0 | 0 | — | — | деления на ноль нет |
| студент без результатов | 2 | 1 | 80.00 | Анна | правило «без результатов» |
| границы категорий | 7 | 7 | 78.14 | G | 59/60/74/75/89/90/100 |

Все ожидания закреплены `assert`-проверками в `demo_scenarios()`.

### Сложность

- `student_summary()` — O(m) по числу оценок студента, память O(1);
- `group_summary()` — O(n) по общему числу оценок (сводки + общее среднее),
  плюс построение рейтинга; память O(k) на сводки по k студентам;
- `build_ranking()` — сортировка вставками O(k²) в худшем случае (для группы
  из десятков студентов это несущественно), исходный словарь не изменяется;
- `find_top_students()` — O(n), один проход.

Общая сложность построения статистики группы — **O(n + k²)**, где n — число
оценок, k — число студентов; доминирует линейный проход.

## Вывод о декомпозиции

Разбиение на небольшие функции с явными контрактами заметно улучшило
читаемость:

1. **Каждая функция отвечает за одно действие.** `mean()` не знает про
   категории, `classify()` — про группы. Из-за этого проверки пишутся
   отдельно от логики (`assert` на маленьких функциях), а не на «монолите».
2. **Повторное использование.** `mean()`, `minimum()`, `maximum()` из
   задания 5 используются и в `group_summary()`, и в `find_top_students()`;
   правило «без результатов» задано в одном месте (`classify(None)`).
3. **Изоляция особых случаев.** Ранние `return` для пустых списков убрали
   проверки из основной ветви вычислений — код читается сверху вниз без
   вложенных `if`.
4. **Тестируемость.** Маленькую функцию с контрактом легко проверить
   доктестом; для интеграционного задания достаточно проверить сводку
   `group_summary()` на шести сценариях, не проверяя форматирование отчёта
   вручную.
5. **Неизменяемость входных данных** вынесена в контракты (`snapshot`,
   `[*results, value]`) и закреплена `assert`-проверками, поэтому исходные
   словари и списки остаются прежними во всех пяти заданиях.

Итог: программа из задания 5 собирается из функций по 10–20 строк,
каждую из которых можно понять и проверить отдельно, тогда как «одна большая
функция» потребовала бы одновременно держать в голове и подсчёт, и формат,
и особые случаи.
